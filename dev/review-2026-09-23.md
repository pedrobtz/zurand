# Review: state of the package and of the roadmap (2026-09-23)

Scope: everything on `main` at `f8fdfc6`, read against the stated goal --
*the go-to package for fast uniform and Gaussian random numbers in R*. The
package's own numbers are taken from `dev/benchmark-baseline.md` (x86_64,
single thread, n = 1e7) and were not re-measured here; three code-level
findings below were verified by compiling small harnesses against the
vendored headers with gcc 13.3 and clang 18.1.

## Verdict in one paragraph

The engineering is well ahead of the packaging. On x86_64 the
`xoshiro256pp` engine with the AVX2 path is already 2.4x dqrng on uniform
and 1.9x RcppZiggurat on Gaussian, which exceeds every target the roadmap
set, and the trust work (KAT against independent references, cross-platform
golden values in hex floats, SIMD-vs-scalar and threads-vs-serial identity
tests, ASan/valgrind/rchk/LTO in CI) is unusually thorough for a package at
version 0.0.0.9000. What stands between this and "go-to" is not more speed.
It is: the default engine is the slowest one; three output-affecting
decisions are being deferred by a "never change the stream" principle that
was adopted before there were any users to protect; the reproducibility
promise has a verified hole on GCC targets with FMA; and the roadmap has no
adoption workstream at all (CRAN, a C API for other packages, vignettes, a
published benchmark). The recommendation is to reframe the roadmap around
one **stream-freeze milestone** before v0.1.0 -- make every output-changing
decision now, deliberately, then freeze -- and to add an adoption phase
that is at least as concrete as the performance phases.

---

## 1. What is good, and should be protected

- **The design is genuinely differentiated.** Stateless keys, typed
  folding, key vectors returning `n x K` matrices, purpose-word domain
  separation, and bit-identical output across threads, platforms and call
  order. No other R package offers this; it is the JAX PRNG model, and it
  is the right model for reproducible parallel simulation.
- **Trust before speed was the right order** and it has paid off: the
  SIMD dispatch and the hybrid engine both landed without changing a bit of
  any existing stream, and the tests prove it rather than assert it.
- **Measurement discipline.** Ratios in the same `bench::mark()` call,
  repeated rounds, platform headers, the `-O2` rule, honest noise
  estimates. The roadmap's two amendments (the generator is not the lever;
  the counter-based constraint was self-imposed) are exactly what a
  measurement-driven plan should produce.
- **The code is readable.** Every non-obvious decision in `src/zurand.c`
  and `src/zurand_engine.h` carries the measurement that justified it.
  The engine-parameterised header (`ZE_*` macros) is the right way to get
  three monomorphic copies of the hot loops without a runtime branch.

## 2. Findings in the code (verified)

### 2.1 Signed-integer overflow in `rng_integer()` for ranges above 2^31

`src/zurand_engine.h`, `fill_integer_column`: `o[j] = min + (int)offset;`
where `offset` is a `uint32_t` below `range`. For
`rng_integer(key, n, -2000000000L, 2000000000L)` the range is 4e9+1,
`offset` can exceed `INT_MAX`, the cast is implementation-defined, and the
addition overflows `int`:

```
ub.c:19:13: runtime error: signed integer overflow: -2000000000 + -544967296
            cannot be represented in type 'int'
```

Two's-complement wraparound happens to give the intended value, so no test
fails; but it is UB, and the sanitizer CI leg cannot catch it because no
test uses a range wider than 2^31 (`test-golden.R` stops at
`max = 2000000000L` with `min = 1L`). Fix:

```c
o[j] = (int)((int64_t)min + (int64_t)offset);
```

and add a golden case with `min = -2000000000L, max = 2000000000L`.

### 2.2 The xoshiro engine's seed is the philox engine's output block

`xoshiro_seed()` seeds sub-chunk `s` from `philox4x64({s, 0, purpose, 0},
key)`. That is the same counter the philox engine uses for its own block
`s` under the same purpose, and `rng_key(seed, engine = ...)` derives the
same key words whichever engine is named. Reproduced in C from the vendored
`philox.h`:

```
philox  rng_bits(rng_key(42), 4, 64)        : c0e6592123d7a06c 0c89edc8a3ba5356 6eb27f65d390675b 73af8b93bd67b8f2
xoshiro rng_bits(rng_key(42, xoshiro), 1, 64): 1b56f8cdd2f1eb5e   <- rotl(s0+s3,23)+s0 of the state above
```

Both match the KAT vectors in `test-kat.R`. So the xoshiro stream for a
seed is a deterministic function of the philox stream for the same seed,
not an independent stream. No user is harmed today, but "compare the two
engines with seed 42" is an obvious thing to do, and the two streams are
then correlated by construction. The reserved fourth counter word exists
for exactly this: seed xoshiro at `{s, 0, purpose, 1}` (or give it its own
purpose range). **This changes xoshiro output and must land before the
stream freezes.**

### 2.3 GCC ignores `#pragma STDC FP_CONTRACT OFF`; the reproducibility promise is open on GCC + FMA targets

The pragma at the top of `src/zurand.c` is guarded by
`__clang__ || __GNUC__ >= 14`. Measured here with `-O2 -mfma` on x86_64:

| compiler | with pragma | without pragma |
|---|---:|---:|
| gcc 13.3 | **1 fused instruction** | 1 |
| clang 18.1 | 0 | 5 |
| gcc 13.3 + `-ffp-contract=off` | -- | 0 |

GCC 13 emits the FMA regardless of the pragma. Whether GCC 14 honours it
was not verifiable here; GCC's documentation has historically said the
pragma is not implemented. On any GCC target where FMA is enabled by
default -- every aarch64 Linux build, i.e. rocker images on Apple Silicon,
AWS Graviton, Raspberry Pi -- `mean + sd * x` and `min + span * u` will be
contracted and the golden tests for non-default `mean`/`sd` and
`min`/`max` will fail there, exactly as they did on macOS arm64 before the
pragma. No CI leg is GCC + aarch64, so this is invisible today.

Fix: `-ffp-contract=off` in `PKG_CFLAGS` (accepted by GCC, clang and the
Rtools toolchain; probe it in the planned `configure` if you want to be
strict about portability), and add an `ubuntu-24.04-arm` leg to
`R-CMD-check` so the golden tests actually run on GCC/aarch64. This turns
roadmap item 3.3 from "nice to have" into a release blocker.

### 2.4 Smaller items

- `rng_uniform()` is documented as returning values strictly inside
  `(min, max)`. That holds for the default bounds; after `min + span * u`
  rounding can return `max` (or `min`) exactly when the bounds are large
  relative to the span, e.g. `min = 1e15, max = 1e15 + 1`. Document it as
  "in `[min, max]`, strictly inside for the default bounds", or clamp.
- `dev/philox.md` says the uniform uses the top 53 bits; the code and
  CLAUDE.md say 52 (`bits >> 12` into a 52-bit mantissa). 52 is right.
- CLAUDE.md is stale in three places: it says `Authors@R` and `License`
  are placeholders (they are filled in), it points at a local path for the
  Random123 upstream (roadmap 4.4), and it does not mention the threefry
  or xoshiro engines, `rng_simd()`, or `src/zurand_engine.h` at all. For a
  file whose job is to orient the next session, that is the most
  important doc drift in the repo.
- `statistical-audit.yml` offers engines `philox4x64`, `threefry4x64`,
  `both`; `xoshiro256pp` -- the engine whose construction most needs the
  audit -- cannot be selected from the workflow, although
  `tools/statistical-audit.R` supports it.
- GitHub issue #11 lists 0.2 (golden tests) as open; it shipped in PR #3.

## 3. The strategic review

### 3.1 The default engine is the slowest one

`rng_key(seed)` gives `philox4x64`: 314 M/s uniform (0.96x dqrng) and
215 M/s Gaussian (1.09x RcppZiggurat). The package whose goal is "fastest
uniform and Gaussian in R" ships a default that ties dqrng. Every README
example, every third-party benchmark, and every "I tried it" blog post
will use the default; almost none will pass `engine = "xoshiro256pp"`.

The roadmap's principle -- *the default stream never changes* -- is the
right principle for a released package. It was adopted at 0.0.0.9000, with
no users, and it is now costing the package its headline. What philox
preserves (O(1) access to an arbitrary index) is not exposed by any
exported function, as the roadmap itself notes.

**Recommendation: make `xoshiro256pp` the default before v0.1.0**, keep
`philox4x64` and `threefry4x64` as opt-in engines, and write the decision
into the log. Two conditions first:

1. Run the long statistical audit the roadmap already requires (hundreds
   of GB of PractRand on `normal` and `uniform`) on `xoshiro256pp`
   specifically. Reseeding xoshiro every 512 words from Philox is a novel
   construction; 512 MB is a smoke test. Add `xoshiro256pp` to the
   workflow's engine input so this can run in CI.
2. Fix 2.2 first, since the stream changes anyway.

### 3.2 There is one window to change output. Use it on purpose, then close it

Beyond the default engine, three more changes alter output and are each
individually justified:

| change | why | roadmap item |
|---|---|---|
| domain-separate the xoshiro seed from the philox stream | finding 2.2 | new |
| fuse `mean`/`sd` into the ziggurat transform | removes a second full memory pass on every non-default `rnorm`-style call; the fused rounding differs from the two-pass one | 1.3 |
| (optional) round `rng_uniform()` bounds handling so `[min, max]` semantics are exact | 2.4 | new |

Each is cheap. None can land after v0.1.0 without a new engine name. The
roadmap should have an explicit **"stream freeze" milestone**: every
output-affecting change goes in before it, the golden files are
regenerated once with a commit that says so, and after it the current
principle applies for good.

### 3.3 The threading headline is real on Linux and Windows, not on macOS

Roadmap 3.2 is right that bit-identical threaded fills are a moat no
competitor has. Two caveats belong in the plan:

- **CRAN macOS binaries are built without OpenMP** (Apple clang has none;
  this is the reason for data.table's well-known "no OpenMP" message on
  macOS). Mac users installing from CRAN get a single-threaded zurand
  unless they build from source with libomp. On the platform most R
  laptops run, the single-thread number is the number.
- **CRAN's check farm limits packages to two cores.** The test suite draws
  above `ZURAND_OMP_MIN_VALUES` with no cap set. Verify that the OpenMP
  runtime honours CRAN's `OMP_THREAD_LIMIT` under `R CMD check --as-cran`,
  or cap `rng_threads(2L)` at the top of the tests. This is a common
  reason for a CRAN bounce.

Consequence: the NEON path (5.2) matters more for Mac users than
threading does, and it is unstarted. GitHub's `macos-14`+ runners are
Apple Silicon, so the benchmark workflow can produce M-series numbers today;
the roadmap's "primary machine" has never produced a baseline.

### 3.4 Gaussian is the harder half, and the plan has parked it

Uniform is at 776 M/s against a ~1200 M/s allocation floor; the remaining
lever there is NEON. Gaussian is at 376 M/s, half the uniform rate, and the
roadmap calls a SIMD-friendly transform "a research problem". It is more
bounded than that:

1. **Land 1.2 (packed `{ki, wi}` table)**: measured +10% on the
   transform, +4% end to end, one generated header. Trivial.
2. **Land 1.3 (fused `mean`/`sd`)**: before the freeze, see 3.2.
3. **Prototype an AVX2 fast path for the ziggurat** in `dev/simd/`,
   scalar fallback for rejected lanes. The pieces exist: two gathers
   (`ki`, `wi`), a 64-bit compare, and the int-to-double conversion that
   AVX2 lacks is not needed -- `rabs` is 52 bits, so the magic-number
   trick `(double)(rabs | 0x4330000000000000) - 2^52` is exact. The
   rejection rate is ~1%, so a `movemask` and a scalar loop over rejected
   lanes keeps the output bit-identical. Gather cost on Coffee Lake is the
   unknown the roadmap already named; measure it in a week, not a quarter.
4. If (3) does not pay, accept ~400 M/s single-thread and let threading
   carry the headline on Linux/Windows.

A realistic single-thread Gaussian target is 500 M/s on AVX2. Anything
beyond needs a different sampler family and is out of scope.

### 3.5 The adoption workstream is missing

dqrng is the incumbent because of CRAN, a header-only API other packages
`LinkingTo`, `dqsample`, vignettes, and years of presence -- not because
it is fastest. The roadmap's Phase 4 has four small items. It needs:

| item | why it matters | effort |
|---|---|---|
| **C API for package authors**: `inst/include/zurand.h` plus `R_RegisterCCallable()` for the fill functions (`out`, `n`, key words, engine, purpose args) | This is the in-place fill API that PR #4 tried and rightly closed, delivered where it is safe: a C caller owns its buffer, so there is no copy-on-write question. Simulation, MCMC and bootstrap packages are the multiplier for "go-to" | 2 days |
| CRAN release (0.1.0) | Nothing off CRAN is go-to | after freeze |
| Two vignettes: "why stateless" and "performance" (the benchmark table with platform header, single- and all-threads) | The README has no benchmark table; the case for the package is currently in `dev/` | 1 day |
| pkgdown site, NEWS.md | Standard expectations | half day |
| `rng_exponential()` | NumPy's exponential ziggurat tables are already vendored in the same header; the sampler is ~40 lines mirroring the normal one. Exponential is the next thing every simulation needs | 1 day |
| A "replacing `rnorm`/`runif`" section | The key is friction for users who only want speed. Do not add a stateful shim (it would undo the design); show the two-line recipe with `rng_key_from_r()` | 1 hour |

### 3.6 Roadmap document hygiene

`dev/roadmap.md` is now a lab notebook: 400 lines with two amendments,
measurement sections and a Phase 5 that is more done than Phase 3. Its
targets table is stale (every target has been exceeded), the Phase 2 items
2.3/2.4 are moot after Amendment 2, the open question about
`philox4x64-7` was answered (rejected), and 3.1 does not record that PR #4
was closed or why. Suggested shape:

1. **Status**: one table of current numbers per platform, single- and
   all-threads, with the date and the machine.
2. **Decisions log**: as now, plus the closed in-place API and the
   default-engine decision.
3. **Next**: an ordered list, grouped by milestone (stream freeze -> 0.1.0
   -> after), each with its exit criterion.
4. Move the history and measurements to `dev/log.md`.

Keep the measurement protocol section verbatim; it is the best part.

## 4. Proposed ordering

**Milestone A -- stream freeze (all output-affecting work)**

1. Fix 2.1 (UB), 2.2 (xoshiro seed separation), and add
   `-ffp-contract=off` plus an aarch64 Linux CI leg (2.3).
2. Land 1.2 and 1.3.
3. Add `xoshiro256pp` to the audit workflow; run the long PractRand audit
   on it; record results.
4. Flip the default engine. Regenerate golden files once. Tag the freeze.

**Milestone B -- v0.1.0**

5. C API + header; two vignettes; README benchmark table; NEWS; pkgdown.
6. CRAN two-core compliance check; version bump; `cran-comments.md`;
   submit.

**Milestone C -- after release (no output changes)**

7. NEON path for `xoshiro256pp`; M-series baseline from CI.
8. AVX2 ziggurat fast-path prototype; land only if the ratio interval
   separates.
9. `rng_exponential()` as an additive sampler.

Items 7-9 are safe after the freeze because SIMD paths are output-neutral
by construction (the tests already enforce this) and new samplers claim a
fresh purpose value.
